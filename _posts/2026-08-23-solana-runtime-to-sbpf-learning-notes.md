## 1. How I Gradually Dived In

I started with a broad question: what makes up the Solana Runtime, and which parts are most relevant to smart contract execution?

Breaking it down layer by layer produced this model:

```text
Native Validator process
└── Runtime / Bank: manages slots, transaction results, and ledger state
    └── SVM: loads accounts, executes whole transactions, and validates changes
        └── Program Runtime: handles instructions, CPI, syscalls, and CU
            └── SBF VM: actually runs the on-chain program's SBF bytecode
```

The most important clarification is that the SVM and SBF VM are not two VMs of the same kind:

- The SVM is a transaction execution framework implemented as native Rust code inside the Validator.
- The SBF VM is an instruction-level virtual machine with registers, a stack, a heap, memory, and SBF instructions.

## 2. Responsibilities of Bank, SVM, and Program Runtime

The responsibility chain for one transaction is:

```text
Bank prepares the current slot's execution environment
→ SVM loads accounts and programs
→ Program Runtime executes instructions and CPI
→ SBF VM runs the contract bytecode
→ SVM validates account changes
→ Bank decides what to commit
→ Accounts DB stores new account versions
```

Simple mental model:

- Program Runtime produces the effects of program execution.
- SVM executes the whole transaction and validates its changes.
- Bank applies the success/failure commit rules.
- Accounts DB stores the account versions that Bank commits.

A failed transaction does not necessarily write nothing. Business-state changes are normally rolled back, while fees, durable nonce state, and other protocol-defined changes may still be retained.

## 3. The Public SVM Entry Point

The main SVM entry point is `TransactionBatchProcessor::load_and_execute_sanitized_transactions`.

It performs this flow:

```text
Receive sanitized transactions
→ Load accounts through callbacks
→ Load and cache programs
→ Execute transactions
→ Validate account changes
→ Return processing_results
```

Important interfaces:

- `TransactionProcessingCallback`: decouples the SVM from a specific account database.
- `SVMTransaction`: provides a uniform way to read signatures, accounts, blockhashes, and instructions.
- `TransactionCheckResult`: carries earlier check results such as nonce and fee information.
- `TransactionProcessingEnvironment`: supplies protocol context such as features, fees, rent, and blockhash.
- `TransactionProcessingConfig`: controls logging, simulation, compute budget, and other execution behavior.

`processed` does not mean `successful`: a transaction may reach program execution and still finish with an error.

## 4. Parallel Scheduling Is Outside the SBF VM

Conflict detection and parallel scheduling across transactions mainly happen in the Banking Stage and Central Scheduler:

```text
Scheduler: prioritizes transactions, detects read/write conflicts,
           acquires account locks, and forms batches

SVM: loads and executes transactions in a batch

SBF VM: executes a particular SBF program invocation
```

The SBF VM therefore does not decide which transactions can run in parallel.

## 5. How an On-Chain Program Reaches the SBF VM

The lifecycle of a Rust program is:

```text
Rust source
→ LLVM/Solana toolchain
→ SBF instructions
→ Packaged as ELF
→ Deployed to a ProgramData account
→ Loaded, verified, and cached by a Validator
→ Executed by the SBF VM
```

The chain stores the ELF/SBF program data. The x86_64 machine code generated by JIT exists only in each Validator's local cache and is not stored on-chain.

Relationship among ELF, the verifier, and the execution engine:

```text
ELF: contains code, read-only data, symbols, and entry information
→ ELF Loader: parses it into an Executable
→ Verifier: checks whether the bytecode is valid
→ Interpreter or JIT: executes the program
```

## 6. Interpreter and JIT

Both are ultimately executed by the physical CPU.

Interpreter:

```text
CPU runs the interpreter's native machine code
→ Interpreter reads one SBF opcode
→ Rust logic simulates the opcode's effect on virtual registers and memory
```

For example, the interpreter-side effect of SBF `add64 r1, r2` is similar to:

```rust
registers[1] = registers[1].wrapping_add(registers[2]);
```

JIT:

```text
JIT compiler written in Rust
→ Translates SBF instructions into x86_64 machine code
→ CPU directly executes the generated machine code
```

The interpreter does not run first and then hand the program to JIT. They are two independent implementations of the same SBF semantics. Agave normally prefers an available JIT result and can use the interpreter when JIT is unavailable or when debugging.

## 7. The Six Main Sections of `ebpf.rs`

### 7.1 Basic VM Specifications

This section mainly defines:

- The maximum number of instructions in a program.
- The fixed eight-byte size of an ordinary instruction.
- `r10` as the frame pointer.
- `r6-r9` as registers preserved across calls.

The byte position of instruction `pc` is:

```text
byte_offset = pc × 8
```

### 7.2 Virtual Memory Layout

```text
0 × 2³² → rodata: read-only constants compiled into the ELF
1 × 2³² → bytecode: the current program's SBF instructions
2 × 2³² → stack: local variables and function-call state
3 × 2³² → heap: dynamically allocated data such as Vec and Box buffers
4 × 2³² → input: accounts and arguments for the current instruction
```

These are virtual-address intervals. They do not mean that every region actually allocates 4 GiB of physical memory.

Lifecycle of the input region:

```text
Accounts in TransactionContext
→ Serialized or directly mapped into Input
→ Read and modified by the contract
→ Deserialized back into TransactionContext
→ Validated by SVM
→ Committed by Bank
```

### 7.3 Opcode Encoding

The opcode is the first byte of an instruction. It combines several bit fields:

```text
Instruction class | Operand source | Specific operation
```

For example:

```text
ADD64_REG = 64-bit arithmetic class | register source | ADD
```

### 7.4 Concrete Instructions

Read an instruction name like this:

```text
ADD | 64 | REG
op    width  operand source
```

- `IMM`: the operand is stored directly in the instruction's `imm` field.
- `REG`: the operand comes from another register.
- `32/64`: the operation width.
- Load: copies data from memory into a register.
- Store: copies data from a register into memory.
- Jump: changes `pc` to implement branches and loops.
- Call: enters an internal function or syscall.
- Exit: returns to the caller; at the outermost level it ends the program and returns `r0`.

### 7.5 The `Insn` Structure

After decoding, an eight-byte instruction contains:

```text
ptr: instruction position / pc
opc: opcode
dst: destination register
src: source register
off: memory or jump offset
imm: immediate value carried by the instruction
```

Eight-byte layout:

```text
byte 0      → opcode
byte 1      → src and dst
bytes 2..3  → offset
bytes 4..7  → immediate
```

### 7.6 Helper Functions

- `get_insn`: locates and decodes an instruction using `pc × 8`.
- `augment_lddw_unchecked`: combines two instruction halves into one 64-bit immediate.
- `hash_symbol_name`: converts a function or syscall name into the numeric ID used by calls.

## 8. The Complete Mental Model

```text
Transaction scheduler selects executable transactions
→ Bank supplies slot and protocol context
→ SVM loads accounts and programs and processes the whole transaction
→ Program Runtime creates the invocation context
→ SBF VM maps bytecode, stack, heap, and input
→ Interpreter/JIT executes opcodes
→ Syscalls enter the host runtime when needed
→ Account changes return to TransactionContext
→ SVM validates the changes
→ Bank commits
→ Accounts DB stores the result
```
