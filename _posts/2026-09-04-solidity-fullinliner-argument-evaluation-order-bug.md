## Overview

This bug was a miscompilation issue in Solidity's Yul optimizer.

Yul defines function argument evaluation order as **right-to-left**, but older versions of `FullInliner` could, under specific conditions, transform argument binding into **left-to-right** order.

If the arguments had no side effects, this usually did not change the result.

If the arguments contained operations such as:

- `sstore`
- `mstore`
- `revert`
- `return`
- event / log emission
- external calls
- other state-changing or control-flow-changing operations

then changing evaluation order could directly change program semantics.

Affected versions:

```text
Solidity 0.6.7 ~ 0.8.20
```

Fixed in:

```text
Solidity 0.8.21
```

This is a:

```text
miscompilation
```

meaning:

```text
source semantics
!=
generated bytecode semantics
```

---

## 1. What FullInliner Does

`FullInliner` is an optimization pass in the Yul optimizer.

It transforms code like:

```yul
function f(x) -> r {
    r := add(x, 1)
}

let a := f(10)
```

into something approximately like:

```yul
let x_tmp := 10
let r_tmp := add(x_tmp, 1)
let a := r_tmp
```

The function call itself disappears and the function body is copied into the call site.

The purpose is:

```text
remove function boundaries
↓
expose more expressions
↓
allow later optimizer passes to optimize further
```

---

## 2. Yul Argument Evaluation Order

Yul evaluates function arguments:

```text
right-to-left
```

For example:

```yul
f(a(), b())
```

the correct execution order is:

```text
b()
↓
a()
↓
f(...)
```

not:

```text
a()
↓
b()
↓
f(...)
```

As soon as the arguments contain side effects, this order becomes part of the program's semantics.

---

## 3. Why Evaluation Order Can Affect Security

Consider:

```yul
function write() -> r {
    sstore(0, 100)
    r := 100
}

function read() -> r {
    r := sload(0)
}

add(read(), write())
```

With correct Yul evaluation order:

```text
write()
↓
storage[0] = 100
↓
read()
↓
reads 100
↓
result = 200
```

If incorrectly changed to left-to-right:

```text
read()
↓
reads old value, for example 5
↓
write()
↓
storage[0] = 100
↓
result = 105
```

The same program now produces a different result.

This is not merely a difference in optimization quality. The program semantics have changed.

---

## 4. What ExpressionSplitter Does

`FullInliner` originally relied on `ExpressionSplitter`.

For example:

```yul
f(a(), b())
```

would first be split into:

```yul
let tmpB := b()
let tmpA := a()

f(tmpA, tmpB)
```

This already fixes the side-effect order as:

```text
b()
↓
a()
```

After that, FullInliner sees:

```yul
f(tmpA, tmpB)
```

where the arguments are only:

```text
Identifier
```

At that point, inlining normally no longer changes side-effect order.

---

## 5. The Implicit Invariant

FullInliner depended on the following precondition:

```text
input to FullInliner has already been expression-split
```

In other words, it expected:

```yul
f(x, y)
```

rather than:

```yul
f(a(), b())
```

The default optimizer pipeline originally guaranteed this invariant:

```text
ExpressionSplitter
↓
FullInliner
```

---

## 6. How the Invariant Broke

Starting with Solidity 0.6.7, custom Yul optimizer step sequences became configurable.

This made it possible to run:

```text
FullInliner
```

without first running:

```text
ExpressionSplitter
```

It was also possible to have a sequence such as:

```text
ExpressionSplitter
↓
ExpressionJoiner
↓
FullInliner
```

where `ExpressionJoiner` could recreate complex expressions.

As a result, FullInliner could receive code such as:

```yul
f(a(), b())
```

The invariant it depended on was no longer guaranteed.

---

## 7. How the Bug Happens

Assume:

```yul
function f(a, b) -> r {
    r := add(a, b)
}
```

and the call:

```yul
f(ret(), rev())
```

The correct evaluation order is:

```text
rev()
↓
ret()
↓
f(...)
```

An older FullInliner could produce temporary bindings similar to:

```yul
let tempA := ret()
let tempB := rev()
```

This changes execution order to:

```text
ret()
↓
rev()
```

The argument evaluation order has been reversed.

---

## 8. Classic PoC

```yul
function rev() -> r {
    revert(0, 0)
}

function ret() -> r {
    return(0, 0)
}

f(ret(), rev())
```

Correct semantics:

```text
rev()
↓
revert
↓
execution terminates
```

Therefore the result should be:

```text
REVERT
```

After incorrect inlining:

```yul
let tempA := ret()
let tempB := rev()
```

execution becomes:

```text
ret()
↓
RETURN
↓
execution terminates
```

`rev()` is never executed.

The result changes from:

```text
REVERT
```

to:

```text
RETURN
```

---

## 9. The Fix

The current FullInliner creates parameter bindings using logic equivalent to:

```cpp
for (
    auto&& [parameter, argument]:
    ranges::views::zip(
        function->parameters,
        _funCall.arguments
    )
    | ranges::views::reverse
)
    newVariable(parameter, &argument);
```

Assume:

```text
parameters = [a, b]
arguments  = [ret(), rev()]
```

After:

```cpp
zip(parameters, arguments)
```

the pairs are:

```text
(a, ret())
(b, rev())
```

Without reversing the iteration order:

```text
(a, ret())
↓
(b, rev())
```

the generated bindings would be:

```yul
tempA := ret()
tempB := rev()
```

which evaluates left-to-right.

With:

```cpp
ranges::views::reverse
```

the order becomes:

```text
(b, rev())
↓
(a, ret())
```

and the generated bindings become:

```yul
tempB := rev()
tempA := ret()
```

This restores Yul's required:

```text
right-to-left
```

argument evaluation order.
