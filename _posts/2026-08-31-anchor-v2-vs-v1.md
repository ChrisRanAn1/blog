## Setup 1: Rust Trait

A trait is Rust's version of an "interface." It defines a set of method signatures, and any type that implements those methods is said to "implement" the trait.

```rust
trait Shape {
    fn area(&self) -> f64;                    // required
    fn describe(&self) -> String {             // has a default, can be overridden
        format!("A shape with area {:.2}", self.area())
    }
}

impl Shape for Circle {
    fn area(&self) -> f64 { std::f64::consts::PI * self.radius * self.radius }
}
```

There are three common ways to use a trait: call it directly, use it as a generic bound (`fn f<T: Shape>(x: &T)`), or use it as a trait object (`Box<dyn Shape>`).

### Static Dispatch vs. Dynamic Dispatch

**Generics (static dispatch)**: the compiler knows the concrete type of `T` at compile time and generates a specialized copy of the function for every type actually used (monomorphization). Zero runtime overhead, and the call can even be inlined. The cost is a larger binary.

**`dyn Trait` (dynamic dispatch)**: `&dyn Shape` is a "fat pointer" holding a data pointer plus a pointer to a vtable. Calling `.area()` means looking up the vtable at runtime to find the concrete function. There's overhead and no inlining, but you gain flexibility — this is the only option when you need to mix different concrete types in one collection (`Vec<Box<dyn Shape>>`), or when the type isn't known until runtime.

## Setup 2: The `Accounts` Trait in Anchor

Anchor's account validation is, at its core, a bunch of types each implementing the same trait. Here's the real definition from anchor-lang's source:

```rust
pub trait Accounts<'info, B>:
    ToAccountMetas + ToAccountInfos<'info> + Sized
{
    fn try_accounts(
        program_id: &Pubkey,
        accounts: &mut &'info [AccountInfo<'info>],
        ix_data: &[u8],
        bumps: &mut B,
        reallocs: &mut BTreeSet<Pubkey>,
    ) -> Result<Self>;
}
```

The core rule: **any type that implements this trait must provide a `try_accounts` method — take a bag of accounts, validate them, and return an assembled `Self`.** Here's `Signer<'info>`'s real implementation — the logic is "take the first account, check that it signed":

```rust
impl<'info, B> Accounts<'info, B> for Signer<'info> {
    fn try_accounts(_: &Pubkey, accounts: &mut &'info [AccountInfo<'info>], _: &[u8], _: &mut B, _: &mut BTreeSet<Pubkey>) -> Result<Self> {
        let account = &accounts[0];
        *accounts = &accounts[1..];
        Signer::try_from(account)   // internally, the core check is: if !info.is_signer { error }
    }
}
```

And the `#[derive(Accounts)]` macro does something quite mundane: it **calls each field's own `try_accounts` in order**, then splices in whatever extra constraints you wrote (`has_one`, etc.) as a few `if` checks:

```rust
impl<'info> Accounts<'info, IncrementBumps> for Increment<'info> {
    fn try_accounts(...) -> Result<Self> {
        let counter: Account<'info, Counter> = Accounts::try_accounts(...)?;
        let authority: Signer<'info> = Accounts::try_accounts(...)?;
        if counter.authority != authority.key() {
            return Err(ErrorCode::ConstraintHasOne.into());
        }
        Ok(Increment { counter, authority })
    }
}
```

**The trait is responsible for "each part knowing how to validate itself"; the macro is responsible for "assembling the parts in the order you declared them, and inserting whatever extra constraints you specified."** 

That's the end of the setup. On to the main event.

# Main Event: Anchor v1 vs. v2

Anchor v2's pre-release shipped in April 2026, with a formal introduction in August. The framing from the team is direct: **a shift from a macro-heavy framework to a more extensible, trait-driven architecture**, with binaries up to ~94% smaller and up to ~50× fewer compute units than v1 (per program; see the table below).

Official benchmark numbers (alpha-stage, not final stable values, drawn from the real comparison programs under `bench/programs/`):

| Program | What it exercises | Binary size reduction | CU reduction |
|---|---|---|---|
| `helloworld` | Single-instruction counter, baseline framework overhead | 11.9x | 4.1x |
| `prop-amm` | Oracle feed with an assembly fast path | 11x | 2.8–50.4x |
| `vault` | Single-depositor SOL vault, deposit/withdraw | 17.4x | 3.0–6.1x |
| `nested` | Shared validation logic via `Nested<T>` | 9.4x | 5.5–7.0x |
| `multisig` | Four-instruction SOL multisig with dynamic signer data | 4.5x | 3.0–6.5x |

## Change 1: Constraints Go from String Expressions to Pluggable Traits

This is the clearest example of "macro-driven → trait-driven," and it's where this deep dive spent the most time. Two real-world scenarios, walked through end to end.

### Scenario A: Whitelist Check

Multiple instructions need to check whether a given account address is on a whitelist. v1 gives you exactly one tool for this — `constraint = <expression>` — and you have to hand-write it:

```rust
#[derive(Accounts)]
pub struct DoActionA<'info> {
    pub whitelist: Account<'info, Whitelist>,
    #[account(constraint = whitelist.addresses.contains(&user.key()) @ MyError::NotWhitelisted)]
    pub user: Signer<'info>,
}

#[derive(Accounts)]
pub struct DoActionB<'info> {
    pub whitelist: Account<'info, Whitelist>,
    #[account(constraint = whitelist.addresses.contains(&user.key()) @ MyError::NotWhitelisted)]
    pub user: Signer<'info>,
}
```

### Scenario B: Vault Pause Check

The exact same problem shows up again in a different context:

```rust
#[derive(Accounts)]
pub struct Deposit<'info> {
    #[account(constraint = !pool.is_paused @ MyError::PoolPaused)]
    pub pool: Account<'info, Pool>,
    pub user: Signer<'info>,
}

#[derive(Accounts)]
pub struct Withdraw<'info> {
    #[account(constraint = !pool.is_paused @ MyError::PoolPaused)]
    pub pool: Account<'info, Pool>,
    pub user: Signer<'info>,
}

#[derive(Accounts)]
pub struct Swap<'info> {
    #[account(constraint = !pool.is_paused @ MyError::PoolPaused)]
    pub pool: Account<'info, Pool>,
    pub user: Signer<'info>,
}
```

**Both scenarios expose the same structural problem**: v1 has no independent, nameable, reusable container for "custom validation logic" — it can only exist as a string expression scattered across every `#[account(...)]` that needs it. Change the logic, and you have to hunt down every duplicated copy across the codebase. And the logic can never be unit-tested on its own, because it isn't actually a standalone function.

### v2's Fix: The `AccountConstraint` Trait

v2 turns "a constraint" into a pluggable component. The real trait definition (from `lang-v2/src/traits.rs` on the `anchor-next` branch) is:

```rust
pub trait AccountConstraint<A> {
    type Value;
    fn init(account: &mut A, value: &Self::Value) -> Result<()>;
    fn check(account: &A,     value: &Self::Value) -> Result<()>;
    fn update(account: &mut A, value: &Self::Value) -> Result<()>;
    fn exit(account: &mut A,  value: &Self::Value) -> Result<()>;
}
```

Two things worth noticing right away. First, there's an associated type `Value` — that's the right-hand side of the constraint expression, i.e. the `value` in `#[account(my_ns::key = value)]`. Second, only `check` takes an immutable `&A`; the other three take `&mut A`, because init/update/exit can genuinely mutate the account. The four methods map to four lifecycle moments — creation, validation, update, and exit. Walking through the whitelist example end to end:

**Step 1 — define an empty "marker type" as a label** (it has no fields; its only job is to be a name the macro can reference):

```rust
struct Whitelisted;
```

**Step 2 — write the logic exactly once**. The RHS of the constraint will be the whitelist account, so `Value` is `Account<'info, Whitelist>`:

```rust
impl<'info> AccountConstraint<Signer<'info>> for Whitelisted {
    type Value = Account<'info, Whitelist>;

    fn check(account: &Signer, whitelist: &Account<Whitelist>) -> Result<()> {
        if !whitelist.addresses.contains(&account.key()) {
            return Err(MyError::NotWhitelisted.into());
        }
        Ok(())
    }
    fn init(_: &mut Signer<'info>,   _: &Account<'info, Whitelist>) -> Result<()> { Ok(()) }
    fn update(_: &mut Signer<'info>, _: &Account<'info, Whitelist>) -> Result<()> { Ok(()) }
    fn exit(_: &mut Signer<'info>,   _: &Account<'info, Whitelist>) -> Result<()> { Ok(()) }
}
```

**Step 3 — reference it wherever needed instead of retyping the expression**. The `ns::key = value` syntax passes the whitelist account through as the `Value`:

```rust
#[derive(Accounts)]
pub struct DoActionA<'info> {
    pub whitelist: Account<'info, Whitelist>,
    #[account(whitelisted = whitelist)]
    pub user: Signer<'info>,
}

#[derive(Accounts)]
pub struct DoActionB<'info> {
    pub whitelist: Account<'info, Whitelist>,
    #[account(whitelisted = whitelist)]   // reuses the same logic
    pub user: Signer<'info>,
}
```

The macro sees `whitelisted = whitelist`, looks up "whoever implements `AccountConstraint` under that name," finds `Whitelisted`, and inserts a call to `Whitelisted::check(&user, &whitelist)` in the generated code. The pause-check scenario follows the exact same recipe — implement `AccountConstraint<Account<'info, Pool>>` for a `NotPaused` marker, put `!pool.is_paused` inside `check` (with a `Value = ()` since there's no additional RHS to pass), and reference it from `Deposit`/`Withdraw`/`Swap` — collapsing three duplicated expressions into one implementation referenced three times.

### Full Comparison

| | v1 | v2 |
|---|---|---|
| Where the check logic lives | Inline, as a string expression, inside every `#[account(...)]` that needs it | Written once, as a real Rust type + trait implementation |
| Reusing it | Copy-paste the whole expression | Reference it with one word on a field |
| Changing it | Edit every copy-pasted location, easy to miss one | Edit one implementation; every reference updates automatically |
| Unit-testable on its own | No — it's a fragment of a macro-argument string | Yes — `check` is a plain function you can call from a test |
| Can a third party extend the constraint syntax | Hard — requires modifying which keywords the Anchor macro itself recognizes | Yes — anyone can plug in by implementing `AccountConstraint` |
| Lifecycle coverage | Only the "check" moment (`constraint = ...` only runs during validation) | All four moments are hookable: init, check, update, exit |

The team's real-world example is `anchor-spl`'s namespaced constraints like `token::mint = xxx` and `token::authority = xxx` — these are wired in by implementing `AccountConstraint`. That means `anchor-spl` doesn't need a special carve-out from the Anchor core team; any third-party library can add its own constraint syntax the same way. This is the clearest architectural difference between "macro-driven" and "trait-driven": in v1, which keywords the macro recognizes is hard-coded; in v2, it depends on who has implemented the trait.

## Change 2: Account Storage, from Borsh Deserialization to Zero-Copy (Pod)

### v1: Every Read and Write Requires a "Translation"

An on-chain account is, at bottom, a raw byte slice. v1 defaults to Borsh for converting between bytes and Rust structs:

```rust
#[account]  // v1 defaults to Borsh
pub struct Vault {
    pub owner: Pubkey,
    pub balance: u64,
}
```

The `#[account]` macro generates `AnchorSerialize`/`AnchorDeserialize` implementations for `Vault`. Every read of this account means: grab the raw bytes → parse field by field per the Borsh spec → copy into a freshly allocated `Vault` instance. Writing back after the instruction runs means serializing field by field again. This "parse once, serialize once" cycle executes real code and real memory copies on every access — and that costs CU.

### v2: When the Memory Layout Matches the Byte Layout, Just Use It Directly

```rust
#[account]  // v2 defaults to zero-copy
pub struct Vault {
    pub owner: Pubkey,   // 32 bytes, fixed size
    pub balance: u64,    // 8 bytes, fixed size
}
```

The literal meaning of zero-copy: if a Rust struct's in-memory layout exactly matches the byte layout stored in the account, there's no "parsing" step needed at all — the account bytes simply *are* the struct. Getting there requires three hard constraints, each enforced by a trait or a compile-time check:

1. **Every field must implement `bytemuck::Pod`** — meaning "any bit pattern is a valid value, and there are no internal pointers." `u64` and `Pubkey` satisfy this naturally; `Vec` and `String` do not (they hold pointers into heap memory, not the data itself — outside their original memory context, that pointer is dangling)
2. **The struct must be `#[repr(C)]`** — forces fields to be laid out strictly in declaration order, instead of Rust's default of silently reordering fields for alignment
3. **No hidden padding** — the struct's total size must equal exactly the sum of its field sizes, not one byte more

The `#[account]` macro in v2 automatically generates the corresponding compile-time assertions, `#[repr(C)]`, a `Discriminator` implementation, and an `Owner` implementation — you don't hand-write any of these underlying trait implementations.

**What actually changes when reading through `Account<T>`**:

```rust
// v1: you get a fresh, independent copy of Vault, produced by Borsh parsing
let balance = ctx.accounts.vault.balance;   // the value comes from the parsed copy

// v2: you effectively get a view directly into the account's raw bytes
let balance = ctx.accounts.vault.balance;   // the value is read straight from the account bytes, no parsing step in between
```

The surface code looks nearly identical, but what happens underneath is completely different — v1 is "parse it, convert it, keep a copy"; v2 is "this memory already *is* a `Vault` — just use it."

**When you still need to fall back to Borsh**: accounts with variable-length fields (`String`, `Vec`) can't satisfy `Pod`, so you declare it explicitly:

```rust
#[account(borsh)]   // explicit fallback to Borsh mode
pub struct Profile {
    pub owner: Pubkey,
    pub name: String,           // variable length, can't be zero-copy
    pub friends: Vec<Pubkey>,   // variable length, can't be zero-copy
}
```

That pairs with `BorshAccount<T>` instead of the zero-copy `Account<T>`, and behaves exactly like v1: deserialize on read, serialize on write. **So v2 isn't "Borsh is gone" — it's "Borsh becomes opt-in, reserved for the cases that genuinely need variable-length fields."** Both modes coexist; you pick based on the shape of your data. This is one of the biggest single contributors to the CU reductions in the official benchmarks.

## Change 3: Event Encoding, from Borsh to wincode

### v1: Events Also Go Through Borsh

`#[event]` plus `emit!` writes something that happened on-chain into the transaction log, for off-chain services (frontends, indexers) to listen for:

```rust
#[event]
pub struct OrderFilled {
    pub maker: Pubkey,
    pub price: u64,
    pub size: u64,
}

emit!(OrderFilled { maker: ctx.accounts.maker.key(), price: 1000, size: 5 });
```

`emit!` encodes the struct into bytes and writes them into the transaction log via a syscall. In v1 this encoding step also goes through Borsh, processed field by field — just like account reads and writes, it carries encoding overhead.

### v2: wincode, Compatible Bytes with a VM-Friendlier Implementation

```rust
#[event]  // defaults to wincode
pub struct OrderFilled {
    pub maker: Pubkey,
    pub price: u64,
    pub size: u64,
    pub note: String,  // variable-length fields still supported
}
```

wincode's **wire format** is compatible with Borsh (off-chain listener code doesn't need to change), but its **internal implementation** is tuned for the characteristics of the SBF virtual machine (the VM Solana programs actually run on), coming in roughly 3–10x cheaper than Borsh. **Crucially, it still supports variable-length fields** — unlike zero-copy accounts, which require every field to be `Pod`, wincode is simply a cheaper encoding implementation that doesn't sacrifice flexibility.

If the event's fields genuinely are all fixed-size, there's an even more extreme option:

```rust
#[event(bytemuck)]
#[repr(C)]
pub struct PriceUpdate {
    pub price: u64,
    pub timestamp: u64,
}
```

`bytemuck` mode brings the zero-copy idea to events, doing a raw memory copy of the struct's bytes without running the wincode encoding step at all — just the 8-byte discriminator plus a memcpy. It's the cheapest of the three options, at the cost of no variable-length fields.

| | v1 | v2 default (wincode) | v2 extreme (bytemuck) |
|---|---|---|---|
| Variable-length fields supported | Yes | Yes | No |
| Encoding overhead | Baseline | ~3–10x cheaper | Near zero (raw memcpy) |
| Code changes required | — | Almost none, still `#[event]` | Add `#[event(bytemuck)]` + `#[repr(C)]` |

## Change 4: PDA Bump Values — Computed at Compile Time vs. Searched at Runtime, Every Time

### What a PDA and a Bump Are

A PDA (Program Derived Address) isn't generated from a private key — a program derives it by hashing a set of seeds together with the program ID. To guarantee the resulting address falls in a "no corresponding private key" safe space, the algorithm appends an extra byte — the bump — starting at 255, checking whether the resulting address satisfies the requirement, decrementing and retrying if not, until a valid value is found.

```rust
#[account(seeds = [b"vault", b"v1"], bump)]
pub vault: Account<'info, Vault>,
```

### v1: Re-Searches on Every Single Instruction Execution

Even when the seeds never change and the answer is always the same, v1 still calls `find_program_address` on **every transaction execution**, starting from 255 and hashing repeatedly until it lands on a valid bump. That repeated hashing burns CU on every transaction, even though the result never changes.

### v2: If the Seeds Are Known at Compile Time, Bake the Answer In

```rust
#[account(seeds = [b"vault", b"v1"], bump)]  // both seeds are literals
pub vault: Account<'info, Vault>,
```

The macro inspects the seeds **at the point your program is compiled** (not at runtime) — if `b"vault"` and `b"v1"` are literals already fixed at the moment the code was written, with no dependency on any runtime data, then the answer (what the bump actually is) can also be computed at compile time and turned into a `const` in the generated code:

```rust
// roughly what the macro generates (illustrative)
const VAULT_BUMP: u8 = 253;  // already computed at compile time, baked in here
```

At runtime, on every transaction, the program just reads this constant and does one hash to verify the address — **entirely skipping the "start at 255 and search" loop**.

### The Boundary Case

If the seeds include something only known at runtime (say, an address that depends on the caller), the answer can't be precomputed, and it falls back to v1's runtime search:

```rust
#[account(seeds = [b"vault", creator.key().as_ref()], bump)]
// creator is a runtime-supplied account; the seeds depend on runtime data, so this still searches at runtime
pub vault: Account<'info, Vault>,
```

**The core idea: v1 re-"guesses" the bump on every execution regardless of whether the seeds are fixed; v2 first checks whether the seeds are knowable at compile time — if so, it bakes the answer in and skips the entire "guessing" loop, falling back to the old behavior only when the seeds genuinely depend on runtime data.**

## Change 5: Errors — No More Runtime-Constructed Error Structs with Text Payloads

```rust
#[error_code]
pub enum MultisigError {
    #[msg("Threshold must be between 1 and the number of signers")]
    InvalidThreshold,
    #[msg("Too many signers; max is MAX_SIGNERS")]
    TooManySigners,
}
```

### v1: Errors Assemble a Full Struct with Text, at Runtime

When `err!(MyError::PoolPaused)` or a failed `require!(...)` fires, v1 constructs an `AnchorError` struct **at the moment the program actually runs**, carrying not just the error code but the file name, line number, and the literal text from `#[msg("...")]`. Assembling that struct costs something — especially the text, which is a string that has to be built and handled — and these operations executing on-chain consume compute units. Most of the time, that detail only matters to a human reading logs off-chain; the program's own control flow never touches it.

### v2: The Text Lives Only at Compile Time and in the IDL; the Chain Keeps Only a Number

The text in `#[msg("...")]` is **extracted purely into the generated IDL file** (the client/human-facing interface description, which never participates in on-chain execution). At runtime, on-chain, raising an error does nothing more than write a single numeric error code (e.g., `Custom(6000)`) — it never assembles that text string at runtime, and never records a file name or line number. When the transaction result comes back to the client, the client looks up that numeric code against the local IDL — "what does 6000 mean, what's the message" — and that "translate to human-readable" step happens entirely off-chain, costing nothing on-chain.

| | v1 | v2 |
|---|---|---|
| What actually happens on-chain when erroring | Constructs `AnchorError` (code + file name + line number + text string) | Writes a single numeric error code |
| When the message text is used | At runtime, built into the error struct | Only at compile time, extracted into the IDL — never touched at runtime |
| Where "translate to human-readable" happens | Partly on-chain (string construction) | Entirely off-chain (client looks up the IDL) |
| On-chain overhead | Higher (string operations) | Minimal (writing one integer) |

## Tying the Five Changes Together

```
                v1's philosophy                          v2's philosophy
Constraints    Re-parse a string expression      →   An independent, reusable trait implementation
               into check code, every time
Storage        Convert on every read/write        →   Satisfy Pod and use the memory directly, no conversion
               (Borsh)
Events         Generic Borsh encoding             →   wincode, tuned for the VM, sometimes raw memcpy
PDA bumps      Re-search on every execution        →   Bake the answer in at compile time when seeds are known
Errors         Assemble a text-bearing error       →   Leave just a number at runtime; text moves to compile time
               struct at runtime
```

One sentence to sum up the thread running through all of it: **v1's philosophy is "do a bit more work at runtime, in exchange for simplicity and flexibility while writing the code"; v2's philosophy is "whatever can be pinned down at compile time, pin it down there, and squeeze out every bit of runtime overhead that can be avoided."**
